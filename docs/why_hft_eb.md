# 从回放到实盘，我做了一个事件驱动的高频交易框架

做交易系统，最难的通常不是“再写一个策略”，而是系统还能不能继续演进。

很多项目一开始都很顺：
能接行情，能算信号，能下单，能看日志，好像已经够用了。

但只要系统继续长大，问题很快就会出现：

- 策略、风控、交易接口耦合在一起
- 回测和实盘完全是两套代码
- 新加一个模块，常常得改宿主逻辑
- 柜台适配层和主进程绑死，风险越来越高
- 系统能跑，但越来越难改

`hft_eb` 就是我在这个背景下做的一个项目。

它是一个基于事件驱动架构的 C++17 高频交易框架，目标不是做一个“能下单的 demo”，而是把研究、回放、仿真和实盘接入，放进一套可以持续迭代的工程结构里。

## 我想解决的不是“功能不够”，而是“边界不清”

我更关心的是下面这些问题：

- 行情、策略、风控、交易链路能不能解耦
- 回放和实盘能不能尽量共用同一套运行模型
- 新增一个模块时，能不能不动宿主引擎
- 接入真实柜台时，能不能把高风险部分隔离出去
- 系统能不能先服务研究，再逐步靠近生产

如果这些边界一开始没拆清楚，后面每加一个功能，都会变成维护成本。

## `hft_eb` 的核心思路

这个项目的设计并不复杂，核心就是几件事：

- 用事件总线组织主链路
- 用动态插件扩展模块
- 用 YAML 配置拼装运行拓扑
- 用共享核心状态维护订单、持仓、账户和快照
- 用独立 `trade_gateway` 进程隔离交易柜台
- 用 `hft_md` 和 replay 模块支撑历史行情回放

主引擎 `hft_engine` 自己尽量保持简单，它主要负责：

1. 读取配置
2. 初始化核心状态
3. 按顺序加载模块
4. 驱动事件循环

真正的业务逻辑放在插件里，比如：

- 策略模块
- 因子模块
- 风控模块
- 交易模块
- 回放模块
- 监控模块

典型链路是这样的：

`Replay / 行情 -> Strategy / Factor -> Portfolio -> Risk -> Trade -> Core State / Monitor`

这套结构的价值在于，链路清晰，而且扩展点天然存在。

## 为什么我选择“事件驱动 + 插件化”

因为交易系统本身就天然适合事件驱动。

- 行情到了，是事件
- 因子更新了，是事件
- 策略发出信号，是事件
- 风控批准或拒绝，是事件
- 报单回报、成交回报、账户更新，本质也都是事件

用事件把这些阶段串起来后，模块之间就不需要互相知道太多内部实现，只需要约定事件类型和数据结构。

插件化解决的则是另一类问题：
不要让宿主引擎和每个业务模块写死在一起。

理想情况下，新加一个模块应该只需要：

1. 实现接口
2. 编译成 `.so`
3. 在 YAML 里接进去
4. 跑起来验证

而不是为了加一个策略，先改一圈引擎。

## 这个项目里我比较看重的三个点

### 1. 回放、仿真、实盘尽量走同一套框架

很多系统的问题是研究一套、回测一套、实盘又一套。
结果就是研究结果很难顺滑进入真实运行环境。

`hft_eb` 的做法是尽量统一宿主框架，让差异主要落在模块和配置层。

这样做的好处很直接：
开发、验证、迁移的成本会低很多。

### 2. 独立交易网关进程

真实交易接入往往是最脆弱、最敏感的部分。

所以项目里专门拆出了 `trade_gateway`，把柜台适配层放到独立进程里。这样做不是为了“架构好看”，而是为了降低真实接入时的风险：

- 主引擎和交易接口解耦
- 柜台异常不直接拖垮研究主进程
- 后续替换交易适配器更容易
- 更接近真实生产环境的部署方式

### 3. 面向二次开发

这个项目从一开始就不是封闭应用，而是一个偏框架化的底座。

如果你要新增：

- 策略模块
- 策略树节点
- 因子 DAG 节点
- 风控模块
- 监控模块

理论上都不应该先把整个仓库彻底读透。
你只需要理解公共接口、配置注入方式和几个代表性模块，就能开始改。

## 适合谁关注这个项目

这个项目更适合下面几类人：

- 想搭建自己的交易框架，而不是只写单个策略的人
- 想统一回放、仿真、实盘研发路径的人
- 对事件驱动和插件化架构感兴趣的 C++ 开发者
- 在做量化基础设施或交易中台雏形的人

如果你只是想快速写一个策略脚本，它可能显得偏重。
但如果你已经开始遇到“系统越来越不好改”的问题，这类结构会更有价值。

## 现在已经能做什么

目前仓库里已经有这些核心部分：

- `hft_engine`
- 策略 / 因子 / 风控 / 交易 / 回放等动态模块
- 独立交易网关 `hft_trade_gateway`
- 行情录制器 `hft_md`
- Python / Rust 辅助工具
- YAML 配置驱动的模块拼装方式

从开发者角度看，新人可以比较快完成三件事：

- 把项目编译起来
- 跑通一个 replay / sim 示例
- 按现有接口加一个自己的模块

## 如果第一次看这个仓库，建议这样进入

推荐顺序：

1. 先看 README
2. 再看 `include/framework.h`
3. 再看 `src/engine.cpp`
4. 然后看一个真实配置和几个代表性模块

比如：

- `modules/replay/replay_module.cpp`
- `modules/strategy/simple_strategy.cpp`
- `modules/risk/risk_module.cpp`
- `modules/trade/sim_trade_module.cpp`

这样会比直接全仓库乱翻高效很多。

只要这些边界清楚，后面的演进空间就会大很多。
