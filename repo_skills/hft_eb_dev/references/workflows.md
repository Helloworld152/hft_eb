# 开发与验证工作流

这个文件记录在 `hft_eb` 仓库里做改动时最实用的工作流。只有在准备编码、调整配置、运行验证时再读。

## 开发前定位

- 用 `rg` 搜模块名、事件名、配置字段名，不要先全局浏览。
- 先读目标文件，再读它的头文件、相邻模块和对应设计文档。
- 如果变更涉及多个链路节点，先画清楚“谁发布事件、谁消费事件、谁落盘/转发”。

## 常见改动落点

- 引擎启动、插件装载、配置扁平化注入：`src/engine.cpp`
- 公共接口、事件定义、基类：`include/`、`core/include/`
- 具体业务逻辑：`modules/<name>/`
- 运行开关与参数：`conf/*.yaml`
- 设计依据与行为预期：`docs/`

## 构建入口

### 整仓构建

```bash
./build_release.sh
```

适用场景：
- 需要验证顶层 CMake 是否仍然完整
- 改动跨多个模块
- 用户明确要求完整构建

注意：
- 该脚本默认走 Release 构建
- 会在 `build/` 和 `bin/` 下产生产物
- 顶层 CMake 使用 `FetchContent` 拉取 `ccapi`，无网环境可能卡住或失败

### 轻量测试构建

```bash
cd tests
cmake -B build -DCMAKE_BUILD_TYPE=Release .
cmake --build build -j
```

适用场景：
- 只想验证 `tests/` 下的轻量目标
- 不希望触发整个主工程依赖链

## 验证策略

- 改 `modules/` 单点逻辑：优先做目标文件审查 + 最小构建；若已有对应测试或 harness，再补跑对应验证。
- 改 `conf/*.yaml`：至少检查插件顺序、库名、路径、字段名是否和代码一致。
- 改 `include/` 或事件协议：必须额外检查受影响模块的编译面。
- 改 `src/engine.cpp`：要重点确认配置注入、插件加载、生命周期和运行目录假设。

## 运行相关

### 顶层启动脚本

```bash
./run.sh
```

风险：
- 会 `pkill hft_engine`
- 会等待 15 秒
- 默认启动 `conf/config_real_test.yaml`

只有在用户明确要求启动该链路且确认环境安全时再执行。

### 基准测试

```bash
./tests/run_queue_bench.sh
```

适合在改动底层队列或性能敏感结构后做对照，但它不是全仓回归测试。

## 修改策略建议

- 配置驱动优先：已有 YAML 模式能表达的，不要把参数写死进代码。
- 新行为先找是否已有模块或插件具备类似实现，尽量复用事件和字段命名。
- 不清楚“应该改哪个模块”时，先回到 `docs/modules_overview.md` 和相关设计文档做归属判断。
